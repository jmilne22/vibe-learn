Build an ingest relay

Receive log events over HTTP and write them to a file. Then make your service handle bursts, batch its writes, and shut down without losing accepted work.

Seven steps for pairing with AI. Allow 14–18 hours to implement them, plus time to learn.

The challenge Setup 1. Validate 2. Serve HTTP 3. Write records 4. Add a queue 5. Batch writes 6. Shut down 7. Finish

The challenge

Imagine a small service running beside an application. It receives the application’s logs and appends them to a local file for another process to collect. That service is your ingest relay.

The interesting part starts when events arrive faster than the disk can write them. How much can you keep in memory? When should you reject a request? What happens to accepted events when the process stops? You’ll answer these questions as you build.

Use Go 1.22 or later and the standard library only, including for tests. Declare the Go version in go.mod. Deployment, Kubernetes, authentication, TLS, databases, retries, persistent queues, rotation, crash recovery, and throughput tuning are outside this challenge. You do not need to build the downstream collector.

Before you start

Create an empty project and initialize a module:

go mod init example.com/relay

Pair with AI throughout: ask it to explain unfamiliar concepts, write code with you, and help investigate failures. Work in small changes. Predict what a test will do before running it, and ask why when the result surprises you. No AI transcript or proof of unaided authorship is required.

Examples assume a main package at the module root and bash or zsh with curl. Adjust the build path if you choose another layout. Once you have a server, build it with go build -o relay ., run it in one terminal, and send requests from another.

Each step includes a result to aim for. Outputs are examples, not results from an existing implementation. Test names, timings, JSON member order, and error wording may differ; statuses and behavior must match. Use a fresh process and a new output file for each independent example unless stated otherwise.

Optional warm-ups: Go Scratch Exercises.

Build it one step at a time

Work through each step with your pair, and split it when you need more time. Keep the tests from earlier steps as you add behavior. The requirements live here alongside the examples.

Step 1 — Read an event

Start with code that turns JSON into a validated event. You don’t need HTTP yet. Use this as your first input:

{"id":"evt-0001","service":"checkout","level":"info","message":"order placed"}

What to accept

Require exactly one object with four string fields: id, service, level, and message. Reject empty strings and strings containing only Unicode whitespace. Preserve valid values exactly. The level must be precisely debug, info, warn, or error.

Reject missing or unknown fields, non-string values including null, malformed JSON, empty input, and non-object top-level values. Trailing whitespace is fine; another value or other trailing text is not. Choose and document your handling of repeated member names. Event IDs need not be unique; do not deduplicate them.

Turn the input above into tests. Change one thing at a time. For example:

Before moving on, cover every validation rule and accepted edge case. Explain to your pair the difference between malformed JSON and a well-formed event with invalid values.

Step 2 — Put it behind HTTP

Add POST /events and GET /healthz. Support -listen, a non-empty TCP host:port address defaulting to 127.0.0.1:8080. Test successful admission with a test double for now; you’ll connect the actual queue in Step 4.

Handle a request

Check read capacity, body size, validation, and admission in that order. Stop at the first rejection:

  • Allow at most 16 requests to read or validate bodies concurrently. If all slots are occupied, return 503 immediately without reading the body or waiting. Release a slot when reading and validation finish, including on error.
  • Limit bodies to 16,384 bytes after transfer decoding, counting trailing whitespace. Enforce bytes actually read, not just Content-Length; an oversized declared length may be rejected early. Exactly the limit is allowed. Larger bodies get 413, or 400 if invalid input was already detected within the limit. Never admit an oversized body.
  • Invalid events get 400. Do not check Content-Type: valid bodies work regardless of its value or absence.
  • Successful admission gets 202. A full queue or closed admission gets 503, without waiting for space. Handlers never write to the file or wait for storage.

Every rejected event POST must explain the problem. A 400 identifies the field or body error and why it failed; a 503 identifies read capacity, queue capacity, or closed admission. Choose and document response formats, including the success body.

Health returns 200 during normal operation; choose the body. It may return 503 or be unreachable after shutdown begins or storage fails. Other methods on /events return 405; unknown paths return 404.

Try it

Run ./relay, then send an invalid event from the other terminal:

curl -sS -w '\n%{http_code}\n' \
  --data-binary '{"id":"evt-0001","service":"checkout","level":"INFO","message":"order placed"}' \
  http://127.0.0.1:8080/events

Expected: an explanation and status 400

{"error":"level must be debug, info, warn, or error"}
400

Also test both size boundaries (16,384 and 16,385 bytes), success, wrong methods, and unknown paths. Hold 16 requests mid-body in a test; the next must get 503 without its body being read.

Step 3 — Write a record

Now build the file-writing part independently. Support -out, a non-empty path defaulting to events.jsonl. Open the file at startup in append mode, creating it if needed. Never truncate or rewrite existing content.

The output format

Write one complete JSON object followed by a newline per event. Each record has exactly the four original fields plus a server-assigned receive time. The time must come from the UTC clock while handling the request, before admission; use an RFC 3339 string ending in Z. Choose and document its field name and precision.

For a writer test, supply the event from Step 1 and a fixed receive time. With the field name received_at, the appended line should look like:

{"id":"evt-0001","service":"checkout","level":"info","message":"order placed","received_at":"2026-09-23T10:15:30.123Z"}

The real service uses its clock, so real timestamps will differ. JSON member order does not matter. Preserve the event’s string values even when encoding changes how characters are escaped.

Test append behavior with one existing line, then write two records. The result should be three complete lines, with the original line unchanged. Decode the new lines to check their values. Make a write fail and verify that the error reaches the caller. You’ll handle it at service level in Step 6.

Step 4 — Connect the queue

Join the pieces: a handler validates an event, assigns its receive time, and admits it to a bounded queue. Exactly one background worker performs all file writes, in admission order. Concurrent requests need not follow connection arrival order.

Support -queue-size, an integer ≥ 1 defaulting to 128. Queue capacity counts events waiting for the worker, excluding its current batch. Start with one event per write. Keep memory bounded by the 16 read/validation slots, the queue, and one batch. Do not create per-request background work that outlives the request.

See where the events are

Add GET /stats, returning 200 and a JSON object with at least these integers:

FieldMeaning
accepted_totalEvent POSTs answered 202
rejected_totalEvent POSTs answered 400, 413, or 503, each counted once; other paths and methods never count
exported_totalEvents in batches whose write completed fully without error; failed or partial writes count as zero
queue_depthEvents not yet taken by the worker; excludes the current batch, even while being written

Counters start at zero for each process and are not persisted. A statistics request after a client receives its response must reflect that response. The values need not be an atomic snapshot.

Try the whole path

Start a fresh process with ./relay -out step4.jsonl. Send one event:

curl -sS -o /dev/null -w '%{http_code}\n' \
  --data-binary '{"id":"evt-0001","service":"checkout","level":"info","message":"order placed"}' \
  http://127.0.0.1:8080/events

Expected

202

Run curl -sS http://127.0.0.1:8080/stats. Once the write completes, the values should be:

{"accepted_total":1,"rejected_total":0,"exported_total":1,"queue_depth":0}

cat step4.jsonl should show one record like Step 3’s. An immediate stats request can still show work pending; wait for the write before comparing these values.

For a deterministic overload test, use queue capacity 2 and wait until the worker is blocked inside its first write. Submit two more events, then a fourth. Expect three 202 responses, one 503, and:

{"accepted_total":3,"rejected_total":1,"exported_total":0,"queue_depth":2}

Release the write: eventually exported becomes 3 and queue depth becomes 0. Check other rejection counters too, including that 404 and 405 do not affect them.

Step 5 — Write in batches

Replace one-event writes with batches of at most -batch-size events: an integer ≥ 1, default 16. Add -flush-interval: a positive Go duration, default 1s. Queue and batch sizes are independent.

Flush when the batch fills, on each periodic flush opportunity if it is non-empty, and when worker input ends. Never write an empty batch. Pass each batch to storage in a single write. A partial batch waits at most about one interval for a flush opportunity; disk completion time is not guaranteed.

Try it in a controlled test

Use batch size 3 and a writer that records each call. Feed five events and wait until all five have been consumed, holding off the periodic flush. Then trigger one flush opportunity:

Expected write calls

Five events consumed, before the tick13
After the tick23, 2
Another tick, no new events23, 2

Repeat with input ending instead of a tick: the remaining two events must still be written. Choose your test design; do not rely on racing a real timer. Check write counts and contents, not just how many lines eventually appear in a file.

Step 6 — Stop without losing work

Now make the relay safe to stop. Work out who waits for whom with your pair before wiring the shutdown together.

Shutdown and failure

On the first SIGINT or SIGTERM, stop new connections and requests. Let already-running handlers finish their normal checks and admission; they may return 202. Once they finish, close worker input. No event may be admitted after that. Drain the queue, flush the partial batch, then close the file.

Allow one five-second budget from the signal for the whole shutdown. If it expires, report what did not finish and exit nonzero. Choose and document second-signal behavior.

A write error or short write must immediately stop all admission, including from in-flight handlers. Log the failure, shut down HTTP, and exit nonzero within five seconds of failure. An earlier signal-shutdown deadline still applies. No retries are required; unwritten events may be lost and the file may end with an incomplete line. Document that limitation.

Every controlled exit after startup logs final accepted, exported, and rejected totals. Exit 0 only after timely, complete shutdown without storage failure. A crash or forced kill cannot promise final logs.

Try it

Use an output path that does not exist yet. In terminal 1, run ./relay -out step6.jsonl -batch-size 16 -flush-interval 1h. In terminal 2, send an event:

curl -sS -o /dev/null -w '%{http_code}\n' \
  --data-binary '{"id":"evt-0001","service":"checkout","level":"info","message":"order placed"}' \
  http://127.0.0.1:8080/events

After it prints 202, press Ctrl+C in terminal 1, then run there:

echo $?
wc -l < step6.jsonl

Expected: successful exit, one stored event

0
1

The long interval leaves the event in a partial batch; shutdown must flush it. Final logs should report accepted 1, exported 1, rejected 0. Log formatting is yours.

Finish startup checks

Empty, unparseable, or out-of-range flags must report the flag name on standard error and exit nonzero without serving. File-open or address-bind failures must report the cause and exit nonzero. Announce readiness only after both succeed. Log the address and effective configuration, or explain a departure in the README.

For example, ./relay -queue-size 0 should report something like -queue-size must be at least 1 and fail. Also automate draining a nonempty queue, final flushing, stalled shutdown, and no admission after input closes. For write errors and short writes, assert that exported totals do not increase, the failure is reported, and no later event is admitted.

Be precise about success

202 means accepted into memory, not persisted. Exported means a complete successful write handed bytes to the OS. After exit 0, each accepted event appears exactly once in admission order after earlier file content; this is per admission, not per unique ID.

No fsync is required. Power loss, crashes, out-of-memory kills, and SIGKILL may lose data. After a failed write, counters show the gap in fully successful writes, not the exact number of intact records on disk.

Step 7 — Finish something you can explain

You now have the complete relay. Run your checks from a fresh copy:

go build ./...
go vet ./...
go test -race ./...

Expected: build and vet succeed silently; the test command reports success

ok   example.com/relay   1.024s

The package name, timing, and number of lines depend on your layout. Format with gofmt; tests must also pass with plain go test ./... and on repeated runs. Use observable conditions rather than fixed sleeps, and avoid depending on a particular port being free.

Keep the result runnable

Provide source, go.mod, tests, and a README in a repository or archive. Exclude binaries and event output files.

In the README, include run and test commands, the event’s path, ownership of shared state and the file, shutdown order, documented choices, guarantees, and limitations. Note unfinished work and one unfamiliar concept you investigated.

Review correctness, bounded and race-free concurrency, meaningful tests, and clarity. Trace an event with your pair, explain what happens under overload, and predict the effect of changing a limit. If you cannot explain part of the code yet, explore it next with your pair.
