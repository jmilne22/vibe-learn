Build a relay operator

Run your relay on Kubernetes. Then replace hand-maintained manifests with a controller that keeps the workload running and tells you what is happening.

Six steps · 14–18 hours of implementation, plus learning time · Requires your working Ingest Relay.

Setup1. Deploy2. Define the API3. Reconcile4. Roll out5. Report status6. Package

The challenge

Your Ingest Relay works locally. Now run one relay on each worker node, writing logs to that node’s disk. An IngestRelay custom resource will describe the desired configuration; your operator will maintain a DaemonSet and a node-local Service for it.

Use Go, Docker, kind, kubectl, Kubebuilder v4, and Helm. Podman is also fine if you adapt the container commands. Use the Go/tool versions supported by your chosen Kubebuilder release and record them. The allowed modules are controller-runtime, client-go, apimachinery, and scaffold dependencies. See the Kubebuilder setup guide for tool installation.

Pair with AI for explanations, implementation, and debugging. Before changing cluster objects, predict what the controller should observe and change. Webhooks, API conversion, leader election tuning, high availability, OLM bundles, publishing, multi-cluster management, and production hardening are outside the challenge. Your design choices remain yours; explain them in the README.

Outputs below are representative targets, not captured test runs. Names match the examples; hashes, ages, timings, image sizes, and condition messages will vary. Wait for observable readiness rather than copying a fixed sleep.

Prepare a local cluster

Save this as kind.yaml. The two untainted workers let you observe a rollout across nodes.

kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
nodes:
- role: control-plane
- role: worker
- role: worker
kind create cluster --name relay-lab --config kind.yaml
kubectl config use-context kind-relay-lab
kubectl get nodes

Expect three Ready nodes, including relay-lab-worker and relay-lab-worker2. Commands below use the default namespace for relays. Run the controller separately when a command says to keep it running.

Step 1 — Put the relay on both workers

In your relay project, write a multi-stage Dockerfile that produces a static binary and a final image smaller than 50 MB. Use a version tag, never latest. Build and load it into your local cluster:

docker build -t ingest-relay:v0.1.0 .
kind load docker-image ingest-relay:v0.1.0 --name relay-lab
docker image inspect ingest-relay:v0.1.0 --format '{{.Size}}'

The last command must print fewer than 50,000,000 bytes. Choose a runtime image and filesystem permissions that let the relay write its node-local directory; document whether you use an init container, root, or another approach.

Write relay-demo.yaml containing a DaemonSet named relay-demo. Make it listen on 0.0.0.0:8080, mount a hostPath at /var/lib/ingest-relay, and write events.jsonl there. Add readiness and liveness probes on /healthz, at least ten seconds of termination grace, and no control-plane toleration. Use IfNotPresent for the loaded image and label its pods app=relay-demo for the commands below.

kubectl apply -f relay-demo.yaml
kubectl rollout status daemonset/relay-demo --timeout=120s
kubectl get daemonset relay-demo

Expected columns after readiness

NAME         DESIRED   CURRENT   READY
relay-demo   2         2         2

In another terminal, select a specific pod so you know which node's file to inspect. Keep this port-forward running:

RELAY_POD=$(kubectl get pods -l app=relay-demo -o jsonpath='{.items[0].metadata.name}')
RELAY_NODE=$(kubectl get pod "$RELAY_POD" -o jsonpath='{.spec.nodeName}')
kubectl port-forward "pod/$RELAY_POD" 8080:8080

From a request terminal, send an event:

curl -sS -o /dev/null -w '%{http_code}\n' \
  --data-binary '{"id":"operator-1","service":"checkout","level":"info","message":"running on kind"}' \
  http://127.0.0.1:8080/events

Expected

202

After the flush interval, stop the forward with Ctrl+C. In that same terminal, inspect the selected node container:

docker exec "$RELAY_NODE" cat /var/lib/ingest-relay/events.jsonl

Expect a JSON record preserving the four submitted event fields, plus the UTC receive-time field you chose in the relay. The timestamp varies. This is the node container's filesystem, not a path on your laptop. Follow the pod's logs while deleting it from another terminal: expect the relay's clean-exit totals before replacement. Delete relay-demo.yaml before Step 3 so it cannot share the operator's files.

Step 2 — Give the workload an API

Create a separate operator project. These commands scaffold types and a controller; they do not implement reconciliation:

mkdir relay-operator
cd relay-operator
kubebuilder init --domain example.com --repo example.com/relay-operator
kubebuilder create api --group telemetry --version v1alpha1 --kind IngestRelay

Answer yes to resource and controller creation. Define a namespaced telemetry.example.com/v1alpha1 kind IngestRelay with a status subresource. Generate schema validation and defaults for these fields:

Spec fieldType and ruleDefault
imageRequired, non-empty stringNone
queueSizeint32 ≥ 1128
batchSizeint32 ≥ 116
flushIntervalPositive Go duration string; pattern validation1s
portint32, 1024–655358080
hostPathAbsolute path string/var/lib/ingest-relay
resourcesOptional ResourceRequirementsNone

Keep the duration validation consistent with the relay: accept examples such as 500ms and 2s, reject nonpositive values, and document the supported syntax. Add field descriptions and printer columns IMAGE, DESIRED, READY, and AGE.

Run make generate manifests install. Save this as relay.yaml:

apiVersion: telemetry.example.com/v1alpha1
kind: IngestRelay
metadata:
  name: relay
spec:
  image: ingest-relay:v0.1.0
kubectl apply -f relay.yaml
kubectl get ingestrelay relay -o jsonpath='{.spec.queueSize}{" "}{.spec.batchSize}{" "}{.spec.flushInterval}{"\n"}'
kubectl explain ingestrelay.spec

Expected defaults

128 16 1s

The explanation should describe every field. A copy of the resource with queueSize: 0 must be rejected by the API server. At this step the CR can exist without creating any pods; that is the next capability.

Step 3 — Reconcile desired state

Implement reconciliation and keep make run running in the operator project. For each CR, create exactly one DaemonSet and one ClusterIP Service, both in its namespace and named after it. Both carry app.kubernetes.io/managed-by=relay-operator and a controller owner reference to the CR.

The pod inherits the image, resource requirements, port, hostPath, queue size, batch size, and flush interval from the spec. Set -listen to all interfaces on the chosen port, -out to <hostPath>/events.jsonl, and -queue-size, -batch-size, and -flush-interval to their corresponding spec values. Keep the probes, volume, and termination grace from Step 1. Use per-CR pod labels so each Service selects only its own relay. The Service uses the configured port and internalTrafficPolicy: Local.

Revert drift in owned fields and recreate deleted objects within 30 seconds. Let garbage collection remove the DaemonSet and Service when the CR is deleted; do not add a finalizer. Distinguish owned fields from metadata another controller may maintain.

kubectl rollout status daemonset/relay --timeout=120s
kubectl get service relay -o jsonpath='{.spec.type}{" "}{.spec.internalTrafficPolicy}{"\n"}'
kubectl get daemonset relay -o jsonpath='{.metadata.ownerReferences[0].kind}{"\n"}'

Expected

ClusterIP Local
IngestRelay

Delete the Service and watch for its replacement:

kubectl delete service relay
kubectl get service relay --watch

Expect a new Service within the bound; stop the watch with Ctrl+C. Repeat with an owned field changed manually and verify restoration. In envtest, check creation, selectors, translated arguments, owner references, and drift repair. Use the scaffold’s test target to provision its API-server test binaries; envtest has no kubelet and will not make relay pods Ready for you. Test CR deletion on kind, where garbage collection actually runs, then reapply relay.yaml.

Step 4 — Change configuration safely

A spec change should update the pod template and roll the DaemonSet one pod at a time. Choose and document rollout settings such as maxUnavailable. With healthy storage and graceful pod termination, events acknowledged with 202 must survive the rollout in node-local files. This does not promise survival of node failure or deletion of the kind cluster.

kubectl patch ingestrelay relay --type=merge -p '{"spec":{"queueSize":256}}'
kubectl rollout status daemonset/relay --timeout=120s
kubectl get daemonset relay -o jsonpath='{.spec.template.spec.containers[0].args}{"\n"}'

Expected argument excerpt; formatting and argument order are yours

-queue-size 256

For the drain check, send uniquely identified events through a port-forward, record which requests received 202, then trigger a rollout. The forward may disconnect when its pod disappears; reconnect as needed. Wait for completion and compare the accepted IDs against records on both worker disks. Rejected or disconnected requests are not acknowledgements.

Reconciliation must also be quiet when nothing changes. In a controlled envtest, reconcile an already-correct resource again and compare the DaemonSet and Service resourceVersions: they must be unchanged. Test a spec update separately and assert that its intended template fields change. A live cluster’s status updates can change versions independently, so it is not a reliable no-op test.

Step 5 — Report what is happening

Populate status.observedGeneration with the generation successfully reconciled, and mirror the DaemonSet’s desiredNumberScheduled and numberReady. Give each condition a CamelCase reason and a useful message:

  • Available=True when desired is greater than zero and ready equals desired.
  • Progressing=True while the DaemonSet’s observed generation or updated counts lag the current template.
  • Degraded=True after a reconcile failure, or under your documented broader failure definition.

Do not treat an API update succeeding as evidence that replacement pods are healthy. Use envtest to supply DaemonSet status and check the CR’s counts, conditions, and observed generation.

kubectl wait --for=condition=Available ingestrelay/relay --timeout=120s
kubectl get ingestrelays

Expected after reconciliation and readiness

NAME    IMAGE                   DESIRED   READY   AGE
relay   ingest-relay:v0.1.0      2         2       2m

Try an unavailable image, inspect pod events and CR conditions, then restore the working version:

kubectl patch ingestrelay relay --type=merge -p '{"spec":{"image":"ingest-relay:missing"}}'
kubectl get ingestrelay relay -o yaml
kubectl patch ingestrelay relay --type=merge -p '{"spec":{"image":"ingest-relay:v0.1.0"}}'
kubectl rollout status daemonset/relay --timeout=120s

Once a replacement cannot start, expect a rollout in progress and counts reflecting reality. Report Degraded according to your documented rule; never invent readiness. Conditions can be briefly stale while changes propagate.

Step 6 — Package a repeatable installation

Build an operator image and a Helm chart at charts/relay-operator. Install the CRD, required RBAC, and operator in its own namespace under its own service account. Make the operator image and resources configurable through values. For these examples, expose image.repository and image.tag, and use IfNotPresent for local images.

Grant only the permissions reconciliation needs: IngestRelay resources and their status, DaemonSets, Services, and events if emitted. Run one controller replica for this exercise; avoid requiring cluster-admin. Stop the local make run process before starting the packaged controller.

make docker-build IMG=relay-operator:v0.1.0
kind load docker-image relay-operator:v0.1.0 --name relay-lab
helm lint charts/relay-operator
helm upgrade --install relay-operator charts/relay-operator \
  --namespace relay-system --create-namespace --wait --timeout=2m \
  --set image.repository=relay-operator --set image.tag=v0.1.0
kubectl wait --for=condition=Available ingestrelay/relay --timeout=120s

Expected final command output

ingestrelay.telemetry.example.com/relay condition met

Check the packaged controller by keeping this forward running:

kubectl port-forward daemonset/relay 8080:8080

In a second terminal, send a new event:

curl -sS -o /dev/null -w '%{http_code}\n' \
  --data-binary '{"id":"packaged-1","service":"checkout","level":"info","message":"installed with Helm"}' \
  http://127.0.0.1:8080/events

Expect 202 and a matching stored record on the selected worker. Then script the complete installation on a fresh kind cluster: create it, load both images, install the chart, apply the CR, wait for Available=True, send an event, and verify its record. Give readiness checks a timeout and fail clearly when any command fails. A successful install into a cluster that already has your CRD is not sufficient.

Document Helm upgrade/uninstall effects on CRDs and existing CRs. Helm’s crds/ directory installs definitions but does not normally upgrade or delete them; make your chosen handling explicit. See Helm’s CRD guidance.

Finish

make test
helm lint charts/relay-operator

Expect the controller tests to pass and the chart to be lint-clean. Keep a separate end-to-end result showing the real cluster reached readiness. In the rollout test, track response statuses as well as file contents; a client connection failure must not quietly become a missing “accepted” event.

Provide the relay Dockerfile, operator source and tests, chart, and an end-to-end script. The README should get a fresh cluster to Available=True and explain the API defaults, ownership, drift repair, rollouts, conditions, RBAC, filesystem permissions, Helm behavior, and unfinished work. Review with your pair why reconciliation converges and why an unchanged desired state produces no resource writes.
