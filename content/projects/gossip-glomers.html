The challenge

This is a guided route through Fly.io’s distributed-systems challenges, tested by Jepsen’s Maelstrom. Each process is a node, messages travel over simulated networks, and the harness checks histories. The linked official stage specifications remain authoritative. This page adds a build-and-check rhythm, not a replacement consistency model.

Use Go and Maelstrom’s Go library, github.com/jepsen-io/maelstrom/demo/go; no other third-party modules. Pair with AI for explanations and implementation. Ask what must remain true when messages are delayed, duplicated, or cannot cross a partition. Compare published solutions after your own approach passes and record what you learn.

Set up once

Install Go, a JDK compatible with Maelstrom, Graphviz, and gnuplot. These examples use Maelstrom 0.2.3, the release used by Fly’s challenge instructions. Keep a record of actual tool and Go library versions in your README.

mkdir gossip-work
cd gossip-work
GG_ROOT="$(pwd)"
mkdir -p "$GG_ROOT/bin"
curl -fLO https://github.com/jepsen-io/maelstrom/releases/download/v0.2.3/maelstrom.tar.bz2
tar xjf maelstrom.tar.bz2
"$GG_ROOT/maelstrom/maelstrom" --help

Expect usage text. Keep this terminal’s GG_ROOT for the commands below. Create six source directories inside it: echo, unique-ids, broadcast, counter, kafka, and txn. Initialize a module and fetch the library in each. For example:

mkdir -p "$GG_ROOT/echo"
cd "$GG_ROOT/echo"
go mod init example.com/maelstrom-echo
go get github.com/jepsen-io/maelstrom/demo/go

After writing each main package, build it from its source directory to $GG_ROOT/bin/maelstrom-NAME, substituting its directory name. Rebuild after every change. The harness commands below run from the extracted Maelstrom directory.

Protocol examples show bodies only and omit message IDs for readability. Real messages include source, destination, and request/reply correlation; use the library’s node and reply handling. Keep diagnostics on stderr so stdout contains only protocol messages. The harness injects network faults, not process crashes, so these challenges do not require disk persistence.

Expected outputs are targets, not claimed runs. Every stage requires a valid result. Inspect store/latest/results.edn, node logs, and message diagrams; ./maelstrom serve exposes a local results browser. A protocol example alone does not prove correctness.

1 — Echo

Make a node receive an echo request and return the same value with an echo_ok type. Preserve the connection between the reply and its request. This is your first check that a Go binary can participate in the harness.

Example request body

{"type":"echo","echo":"hello relay"}

Expected response body

{"type":"echo_ok","echo":"hello relay"}

From the echo directory, build with go build -o "$GG_ROOT/bin/maelstrom-echo" .. Check malformed handling without contaminating stdout with debug prints.

Run it

cd "$GG_ROOT/maelstrom"
./maelstrom test --bin "$GG_ROOT/bin/maelstrom-echo" -w echo --node-count 1 --time-limit 10

Expected

Everything looks good!

Official stage: 1 — Echo.

2 — Unique IDs

Create the unique-ids binary. Every generate request must return a globally unique ID, even while nodes cannot communicate. The representation is yours; a process-local counter alone is insufficient across multiple nodes.

Example request body

{"type":"generate"}

Expected response body

{"type":"generate_ok","id":"n1-42"}

The example ID is illustrative: check uniqueness, not that literal value. Explain why concurrent requests on one node and requests on different nodes cannot collide. Availability must not depend on reaching a coordinator.

Run it

cd "$GG_ROOT/maelstrom"
./maelstrom test --bin "$GG_ROOT/bin/maelstrom-unique-ids" -w unique-ids --time-limit 30 --rate 1000 --node-count 3 --availability total --nemesis partition

:valid? true

Official stage: 2 — Unique IDs.

3a — Remember broadcasts on one node

Start the broadcast binary with handlers for broadcast, read, and topology. Store received integer values as a set. A broadcast returns broadcast_ok; a topology message returns topology_ok. Reading returns known values in any order.

Example request body

{"type":"broadcast","message":7}

Expected response body

{"type":"broadcast_ok"}

After storing 7 and 11, a read can return {"type":"read_ok","messages":[7,11]}. Repeated delivery of 7 must not create duplicates. Unit-test deduplication before adding network propagation.

3b — Share broadcasts across nodes

Propagate stored values to the other nodes. You may follow the supplied topology or choose your own. Keep the client protocol unchanged and make values reach every node within a few seconds on a healthy network.

3c — Survive a network partition

Keep broadcasting while links are unavailable, then converge when communication resumes. Reads return copies of local state. Think through how a value learned just before a partition eventually reaches a node that missed its first delivery.

Example request body

{"type":"read"}

Expected response body

{"type":"read_ok","messages":[7,11]}

The response is an eventual result after healing, not a promise that isolated nodes already agree. Avoid waiting forever for an unreachable peer in a client handler.

Run it

cd "$GG_ROOT/maelstrom"
./maelstrom test --bin "$GG_ROOT/bin/maelstrom-broadcast" -w broadcast --node-count 5 --time-limit 20 --rate 10 --nemesis partition

Expected

:valid? true
All acknowledged values converge by the end of the run.

The second output line describes the required outcome rather than literal harness text. Pass three consecutive runs and record a failure you fixed.

Official stage: 3c — Survive a network partition.

3d — Reduce broadcast latency

Keep the same broadcast/read/topology API. A read still returns a read_ok set of values; optimization must not change its meaning. Now run 25 nodes with 100 ms message latency. Measure the server-to-server message count and stable broadcast latencies.

Example request body

{"type":"read"}

Expected response after the example values are available

{"type":"read_ok","messages":[7]}

Run it

cd "$GG_ROOT/maelstrom"
./maelstrom test --bin "$GG_ROOT/bin/maelstrom-broadcast" -w broadcast --node-count 25 --time-limit 20 --rate 100 --latency 100

Expected

Official stage: 3d — Reduce broadcast latency.

4 — Build a grow-only counter

Create the counter binary with add and read handlers. Back the counter with Maelstrom’s seq-kv service. Concurrent acknowledged additions must not overwrite each other, despite the backing store’s sequential consistency.

Example request body

{"type":"add","delta":5}

Expected response body

{"type":"add_ok"}

From a fresh counter, additions of 5 and 8 should eventually produce {"type":"read_ok","value":13} on every node. Reads may lag while writes are active; final reads must converge to the correct total. Explain how retries avoid double-counting.

Run it

cd "$GG_ROOT/maelstrom"
./maelstrom test --bin "$GG_ROOT/bin/maelstrom-counter" -w g-counter --node-count 3 --rate 100 --time-limit 20 --nemesis partition

Expected

:valid? true

Pass three consecutive runs. Unit-test any merge logic separately from RPCs.

Official stage: 4 — Build a grow-only counter.

5a — Build a single-node log

Create the kafka binary. Each string key identifies an append-only log. Assign increasing unique offsets within a log; gaps are allowed. Poll from an inclusive offset, track committed offsets, and list them for requested keys. Polls need not immediately reveal a new write, but must not lose earlier entries.

Example body exchanges on one fresh log
RequestResponse
{"type":"send","key":"orders","msg":7}{"type":"send_ok","offset":0}
{"type":"poll","offsets":{"orders":0}}{"type":"poll_ok","msgs":{"orders":[[0,7]]}}
{"type":"commit_offsets","offsets":{"orders":0}}{"type":"commit_offsets_ok"}
{"type":"list_committed_offsets","keys":["orders"]}{"type":"list_committed_offsets_ok","offsets":{"orders":0}}

Zero is an illustrative starting offset. Missing keys may be omitted from committed-offset results.

Run it

:valid? true

6a — Execute local transactions

Create the txn binary. A request contains ordered read/write triples. Fill in read results, preserve write operations, and return null for absent keys. Start with one node under the read-uncommitted checker.

Example request body

{"type":"txn","txn":[["r",1,null],["w",1,9]]}

Expected response body

{"type":"txn_ok","txn":[["r",1,null],["w",1,9]]}

This response assumes key 1 was absent. A later read of key 1 should return 9. Explain the visibility of a transaction’s intermediate state to concurrent handlers.

Run it

cd "$GG_ROOT/maelstrom"
./maelstrom test --bin "$GG_ROOT/bin/maelstrom-txn" -w txn-rw-register --node-count 1 --time-limit 20 --rate 1000 --concurrency 2n --consistency-models read-uncommitted --availability total

Expected

:valid? true

Official stage: 6a — Execute local transactions.

6b — Replicate without losing availability

Extend the transaction service to two nodes while keeping read-uncommitted consistency and total availability. Do not block client completion on communication with an isolated peer. Preserve the same request/reply shape.

Example request body

{"type":"txn","txn":[["w",2,17]]}

Expected response body

{"type":"txn_ok","txn":[["w",2,17]]}

The write can complete during a partition. A remote read need not immediately observe 17. Run the healthy network first:

Run it

cd "$GG_ROOT/maelstrom"
./maelstrom test --bin "$GG_ROOT/bin/maelstrom-txn" -w txn-rw-register --node-count 2 --time-limit 20 --rate 1000 --concurrency 2n --consistency-models read-uncommitted --availability total

:valid? true

Then inject partitions:

cd "$GG_ROOT/maelstrom"

Both runs must be valid. Explain your ordering and replication rules; total availability does not mean every consistency model can be supported.

Official stage: 6b — Replicate without losing availability.

6c — Strengthen transaction visibility

Keep total availability, but now pass the read-committed checker. Intermediate or aborted transaction writes must not leak to other transactions. Reason about the checker’s full model, not just one successful example.

Example request body

{"type":"txn","txn":[["w",1,10],["w",1,11]]}

Expected response body

{"type":"txn_ok","txn":[["w",1,10],["w",1,11]]}

Another transaction must not observe the intermediate 10 from this transaction. If you abort for a conflict, Maelstrom’s error code is 30; aborted values must remain invisible. Reads may still be stale across nodes.

Finish with evidence

Keep all six Go projects, exact harness commands, and tool versions. In each module, run go vet ./... and go test ./.... Unit-test pure logic such as ID generation, deduplication, merges, and ownership hashing.

Rebuild each binary with the race detector, for example from the broadcast source directory:

go build -race -o "$GG_ROOT/bin/maelstrom-broadcast" .

Repeat its harness commands. They must remain valid, with no race reports in node logs. Keep non-race builds for comparable efficiency measurements; instrumentation changes timing.

Write a short NOTES.md entry per stage: approach, a failure and what it taught you, consistency and availability assumptions, and tradeoffs. Copy measured 3d/3e and 5b/5c results into a comparison table. Explain why the final design meets its model instead of relying solely on a green run. Mark unfinished stages honestly.

If a run fails, keep its history before the next run replaces the latest pointer. Reproduce it, inspect the relevant messages, and make one reasoned change with your AI pair. Three passing repetitions are useful evidence, not a proof that all executions are safe.
