Go Infra Track · Challenge 04

Build a Tiny TSDB

Store a stream of metric samples, recover it after a crash, and answer time-range queries without keeping the whole history in memory.

Build a single-node time-series database in Go using only the standard library. Metrics arrive as timestamp/value pairs grouped by labels. Your database will acknowledge durable writes, compress samples, move older data into immutable files, and expire those files by retention.

Allow 16–20 hours of implementation, plus time to learn. Experience with the Ingest Relay helps, but this is a separate program. Pair with AI throughout: ask it to explain an unfamiliar idea, predict a small experiment together, and test the resulting code. AI may write code; you should understand and be able to change it.

Package structure, concurrency design, series IDs, and file formats are yours to choose. PromQL, aggregation, remote-write, block compaction, downsampling, histograms, exemplars, staleness markers, replication, and authentication are outside scope.

Step 1: Give each series an identity

Build an in-memory head: the recent samples that have not yet moved into immutable blocks. A series is identified by its complete label set, including __name__. Changing label order must not change identity; changing any name or value must.

Label names must match [a-zA-Z_][a-zA-Z0-9_]*, be unique within a set, and include __name__. Label values must be nonempty UTF-8. Timestamps are signed 64-bit integers in milliseconds; sample values are finite float64 JSON numbers. Within each series, timestamps must increase strictly. Reject a timestamp equal to or earlier than its last stored timestamp.

Step 2: Write and query over HTTP

Add these endpoints. A write is atomic across its entire JSON Lines body, including ordering between lines in that body and concurrent requests. Validate before exposing any part of a rejected batch.

RequestContract
POST /api/v1/writeOne {"labels":{…},"t":int,"v":number} per line. Body limit 1 MiB (1,048,576 bytes). Return 204 for a stored batch, 400 naming the first invalid line and reason with nothing stored, or 413 for an oversized body.
GET /api/v1/queryRequired match, start, end; inclusive millisecond bounds. Return 200 with the shape below. Sort series by canonical label set and samples by ascending time. No matches returns {"series":[]}.
GET /api/v1/series?match=SELReturn 200 with {"series":[{labels},…]}.
GET /healthz200 when serving.
GET /stats200 with series, samples_ingested, head_samples, blocks, chunk_bytes, chunk_samples, and wal_bytes. Extra fields are allowed.

Selectors support equality only: up, up{host="a"}, or {host="a"}. Values need double quotes and there must be at least one matcher overall. Invalid selectors or parameters, including start > end, return 400. Wrong methods return 405; unknown paths return 404. Error response wording is your choice.

Add tests for selector parsing, atomicity, every status above, and the later WAL failure status. Document counter behavior across restarts rather than assuming these lifetime counters persist.

Step 3: Recover acknowledged writes

Add a write-ahead log (WAL). Return 204 only after appending the entire batch and, with the default -wal-fsync=true, syncing it to storage. A WAL failure returns a 5xx and stores nothing. Recovery must never apply a fraction of a batch.

With fsync enabled, acknowledged writes must survive crashes, subject to the storage device honoring synchronization. With it disabled, acknowledgement means appended, without a per-request sync guarantee: a machine crash can lose acknowledged data. Choose and document whether and when you sync in that mode. Killing only the process tests replay; it does not simulate loss of the operating system's write cache.

Try it

Write recovery tests using two batches of 50 increasing samples each. A healthy replay returns 100. Stop the process and truncate three bytes from the final batch record: restart must keep the first 50 and discard the incomplete second batch completely. Also test a checksum-failing final record. Truncate the WAL to its last valid record and log the number of dropped bytes. These deliberately damaged-file tests do not promise recovery of data you removed.

A checksum failure in any nonfinal record must instead stop startup with an error naming the WAL. Include a failing writer test that returns 5xx and exposes no batch data. You choose the record layout and tail-detection method; explain how it distinguishes an incomplete final record from corruption earlier in the log.

Step 4: Compress the samples

Store samples in chunks of at most 120 per series, using Gorilla's delta-of-delta timestamps and XOR-encoded float values. Decoding must reproduce every timestamp and float bit exactly. Within an active sequence of chunks, only the newest may be partly filled; sealing a time window may end its last chunk early. Keep blocks compressed too.

Test bit I/O across byte boundaries, irregular timestamps, negative delta-of-deltas, repeated and fractional values, large values, signed zero, and NaN payloads at the encoder level. NaN remains invalid at the HTTP boundary. With 250 samples in one window, expect chunk sizes 120, 120, 10 and a query returning all 250.

Try it

Use these exact reference datasets: 2,880 samples, 15 seconds apart. Define the generator in your request terminal. The gauge values are rounded to two decimals.

gen() {
  LC_ALL=C awk -v name="$1" -v n="$2" -v mode="$3" 'BEGIN {
    t0 = 1700000000000; s = 0
    for (i = 0; i < n; i++) {

      if (mode == "counter") { s += i % 7; v = s }

      printf "{\"labels\":{\"__name__\":\"%s\",\"host\":\"node-1\"},\"t\":%.0f,\"v\":%s}\n", name, t, v
    }
  }'
}

Step 5: Seal immutable blocks

Align time windows to multiples of -block-duration since the Unix epoch. A window is half-open: [start, end). Seal it when the newest head sample reaches end + block-duration / 2. Its immutable block must appear atomically. An interrupted seal must expose no partial block and lose no data. Only remove WAL data once everything it covers is persisted in blocks.

At startup, load existing blocks. Queries must merge blocks and head in order without duplicates. Keep memory proportional to the head, not the full sample history. Once a window seals, reject timestamps before the head's lower bound as out of bounds, even for a previously unseen series.

Step 6: Expire history and stop cleanly

Delete a block when its window end is ≤ newest stored timestamp − retention. Evaluate this after every seal and at startup. Use data time, not the wall clock, and never delete the head. Queries already reading a block must remain safe while retention runs.

Try it

For a boundary test, use fresh data, one-minute blocks, two-minute retention, and one series with timestamps 0, 90000, 179999 and values 1, 2, 3. Two windows seal. Restart, then append timestamp 180000 with value 4 and restart again. No new seal is needed for the second startup to check retention:

179999599992 blocks; sample at 0 remains
180000600001 block; sample at 0 removed; 90000, 179999, 180000 remain

Repeat the reference counter on fresh data with -retention 6h and default two-hour blocks. Expect two blocks and 1,493 samples, starting at 1700020805000. The cutoff is 1700021585000; the three blocks ending at or before 1700020800000 expire. Retention operates on whole windows, so a query can include samples older than the cutoff.

On SIGINT or SIGTERM, stop accepting requests, finish in-flight writes, close the WAL, log final stats, and exit 0. All phases share a five-second budget; failure or timeout must log an error and exit nonzero. Restart should recover only the head from the remaining WAL, alongside the blocks.

Add a programmatic crash loop: on fresh default storage, perform 20 rounds of start, wait for health with a bounded readiness check, write the next 100 samples of the counter dataset, observe 204, kill the process, and wait for it to exit. After a final restart, query all samples. Fail the test on any unsuccessful request rather than counting it as acknowledged.
