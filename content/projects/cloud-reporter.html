Cloud Resource Reporter

Build a Go CLI that lists an organisation's GitHub repositories, calculates summary statistics, and writes table, JSON, or CSV reports.

The command

cloudreport repos --org kubernetes
cloudreport repos --org hashicorp --sort stars --limit 20
cloudreport repos --org prometheus --format json
cloudreport repos --org grafana --format csv > repos.csv

Use Go's standard library. Start with a sequential HTTP client and test it against a local server. The live command reads public GitHub data; it needs internet access, but no account or token. Keep live requests out of your test suite.

FlagMeaning
--orgRequired. One organisation name, not a URL or an owner/repository pair.
--formatDefault: table. table, json, or csv.
--sortDefault: stars. stars, forks, updated descending, or name ascending. Break ties by full repository name ascending.
--limitDefault: 20. Maximum rows displayed. Zero shows all; negative values are errors. Always fetch all pages before applying it.
--timeoutDefault: 30. Positive integer seconds per HTTP request, including reading its body.

Exit 0 after writing a complete report, 2 for invalid arguments, and 1 for fetch, cancellation, or output errors. Write reports to stdout and diagnostics to stderr. A failed fetch must leave stdout empty, even when earlier pages succeeded.

Start a workspace

Create or attach a folder from the Workspace panel. If starting in an external terminal:

mkdir cloudreport
cd cloudreport
go mod init example.com/cloudreport

A main function, an HTTP client, a report calculation function, and a writer are enough to begin. Choose names and file boundaries as the program grows. The stages below include cases for tests you write yourself.

Fetch one page

Make one GET request and decode the response into typed Go values. Use this endpoint and request headers:

GET https://api.github.com/orgs/{org}/repos?type=public&sort=full_name&direction=asc&per_page=100&page=1
Accept: application/vnd.github+json
User-Agent: cloudreport
X-GitHub-Api-Version: 2026-03-10

Accept only an organisation name in --org; reject blank values, whitespace, and /, \, ?, #, :, and @. Build the request using net/url. Make the API base URL injectable in Go so tests can use httptest.NewServer.

Keep the repository ID, name, full name, stars, forks, language, description, and update time. GitHub calls the count fields stargazers_count and forks_count. Language and description can be null. Use *string if you need to preserve that distinction; the report will display a missing language as Unknown and a missing description as an empty string.

Decode updated_at into time.Time. A malformed timestamp or JSON body is a fetch error. Ignore unknown JSON fields. Close every response body, including error responses, and check the HTTP status before decoding the repository array.

First test

Have a local handler check the request path, query parameters, and headers, then return one repository. Assert its decoded name, count, and timestamp. Add an empty array and a repository with null language and description.

Hint: separate fetching from printing

A method such as FetchPage(ctx context.Context, pageURL string) ([]Repo, string, error) can return repositories and the next-page URL. Leave formatting to its caller. Accept an *http.Client so tests can choose a transport.

Reference: List organisation repositories. API version checked against GitHub's version documentation on 23 September 2026.

Fetch the remaining pages

Follow the URL marked rel="next" in the response's Link header. Stop when it is absent. The number of returned rows does not tell you whether another page exists.

Link: <https://api.github.com/orgs/example-org/repos?page=2&per_page=100>; rel="next", <https://api.github.com/orgs/example-org/repos?page=4&per_page=100>; rel="last"

Fetch pages in order. Preserve the next URL's query parameters. Resolve relative links against the current page and allow only the configured API origin and the same organisation-repositories path. Reject a repeated next URL. Apply the same origin restriction to redirects so an optional token cannot be forwarded elsewhere.

Deduplicate repositories by ID, keeping the first observation. GitHub data can change between requests; pagination does not provide a transactionally consistent snapshot. Sorting by full name reduces movement caused by star or update changes, but repositories can still be added, deleted, or renamed during the run.

Tests to write

  • Two pages: the first has a next link and the second has none. Assert both were fetched.
  • A short first page still has a next link. A full final page has none.
  • The header contains prev, last, and next in a different order.
  • An ID appears on both pages. The report contains it once, using its first values.
  • A next link repeats a visited URL or points at another origin. Return an error without requesting it.
  • Page two returns 500 or invalid JSON. Return an error and no partial report.
Hint: make the loop's state visible

Track the next URL, visited URLs, and IDs already collected. Fetch and validate one page before updating those collections. Keep this loop independent of sorting and output limits.

Reference: GitHub pagination.

Calculate the report

Calculate the total repository count, total stars, repositories per language, and the count updated within the last seven days. Use all collected repositories for the summary, then sort and limit the displayed rows.

Capture the current time once per run and pass it into the calculation. Count timestamps from now - 7 × 24 hours through now, inclusive. Exclude future timestamps. Use ordinary string ordering for names and language labels; use full name to break numeric or timestamp ties.

A fixed example

The following is a constructed dataset. In tests, set now to 2026-09-23T12:00:00Z.

[
  {"id":1,"name":"alpha","full_name":"example-org/alpha","stargazers_count":8,"forks_count":2,"language":"Go","description":"API, workers","updated_at":"2026-09-22T12:00:00Z"},
  {"id":2,"name":"beta","full_name":"example-org/beta","stargazers_count":8,"forks_count":4,"language":null,"description":null,"updated_at":"2026-09-01T12:00:00Z"},
  {"id":3,"name":"gamma","full_name":"example-org/gamma","stargazers_count":3,"forks_count":1,"language":"Go","description":"Queue tools","updated_at":"2026-09-20T12:00:00Z"}
]

With --sort stars --limit 2, display alpha then beta. The summary is still 3 repositories, 19 stars, Go: 2, Unknown: 1, and 2 recently updated.

Tests to write

Cover every sort mode, ties, zero limit, a limit larger than the dataset, empty input, and timestamps exactly at and just outside the seven-day boundary. Add a future timestamp. Verify that changing the display limit never changes summary totals.

Hint: test this without HTTP

Pass a slice of repositories and a fixed time directly into the report function. Copy the slice before sorting if callers need its original order. Use sort.Slice or slices.SortFunc with the tie-break rule in the same comparator.

Write table, JSON, and CSV output

All formats use the same selected rows. Only the presentation changes. The examples below use the fixed dataset and --sort stars --limit 2.

Table

Repository report: example-org
Repositories: 3 (showing 2)

NAME   STARS  FORKS  LANGUAGE  UPDATED
alpha  8      2      Go        2026-09-22
beta   8      4      Unknown   2026-09-01

Total stars: 19
Languages: Go (2), Unknown (1)
Updated in last 7 days: 2

Use UTC dates and align columns; spacing is your choice. Sort language labels alphabetically. text/tabwriter handles alignment without hand-calculating column widths. Check its flush error.

JSON

{
  "org": "example-org",
  "summary": {
    "total_repos": 3,
    "total_stars": 19,
    "languages": {"Go": 2, "Unknown": 1},
    "updated_last_7_days": 2
  },
  "repos": [
    {"name":"alpha","full_name":"example-org/alpha","stars":8,"forks":2,"language":"Go","description":"API, workers","updated_at":"2026-09-22T12:00:00Z"},
    {"name":"beta","full_name":"example-org/beta","stars":8,"forks":4,"language":"Unknown","description":"","updated_at":"2026-09-01T12:00:00Z"}
  ]
}

Use these field names and types. Emit an empty array for no repositories and an empty object for no languages. Pretty-print the result; object key order is irrelevant. Keep timestamps in UTC RFC3339 format.

CSV

name,full_name,stars,forks,language,updated_at,description
alpha,example-org/alpha,8,2,Go,2026-09-22T12:00:00Z,"API, workers"
beta,example-org/beta,8,4,Unknown,2026-09-01T12:00:00Z,

CSV contains a header and repository rows only. Use encoding/csv for commas, quotes, and newlines in descriptions. Flush the writer and check Error(). For an empty organisation, write only the header.

Tests to write

Decode JSON output before comparing values; parse CSV output back into records. Check the table's row order and totals. Add descriptions containing commas, double quotes, and newlines. Supply an io.Writer that returns an error and verify that formatting reports it.

A writer can fail after writing some bytes. Exit 1 and report that failure on stderr; fetching successfully does not make a failed write a successful command.

Handle failures and cancellation

A one-shot report can stop and explain an API failure. The core command does not automatically retry or wait for a rate-limit window.

Response or failureCommand behaviour
401Report an authentication error.
404Report that the organisation was not found or is inaccessible.
403 or 429 with rate-limit detailsReport the limit and any retry time supplied by GitHub. Stop fetching.
Other non-200 responseReport the status and a bounded excerpt of its message. A 403 without rate-limit evidence may be an access error.
Invalid JSON, interrupted body, timeout, or connection failureIdentify the failed page and return the error.
Ctrl+CCancel the active request and stop fetching more pages.

Unauthenticated requests normally share an IP-based budget of 60 per hour. Read X-RateLimit-Remaining and X-RateLimit-Reset from responses. Reset is a Unix timestamp; Retry-After supplies a delay in seconds. Secondary limits can occur with a nonzero remaining count. Missing or invalid headers should not crash the client.

If a successful response reports fewer than ten requests remaining, write a warning to stderr. If the count is zero and another page is needed, stop with an error. If there are no more pages, the report is complete and can be printed.

Use signal.NotifyContext at the command boundary and pass its context through every page request. Release its resources when the command returns. Bound error-body reads, for example to 4 KiB, so an HTML error page does not flood the terminal.

Tests to write

Use local responses for each row in the table. Assert that rate-limit errors never trigger another request and that warnings stay off stdout. For cancellation, have the handler signal that it received the request, wait for its request context to end, then cancel the client's parent context. Use a timeout only to fail a hung test, not to guess when the handler has started.

References: GitHub rate limits and API request guidance.

Run and review the command

go test ./...
go build -o cloudreport .
./cloudreport repos --org kubernetes --format table --limit 5
./cloudreport repos --org kubernetes --format json --limit 5 > report.json
./cloudreport repos --org kubernetes --format csv --limit 5 > repos.csv

On Windows, build cloudreport.exe. Make the live calls once the local tests pass; repository counts and timestamps will differ from the constructed example. Check the process exit status as well as the files. In the app, attach this folder and use Your tests to run your suite.

Review questions

Why fetch every page when the limit is five?

The display sort may differ from the API order, and the summary covers the whole organisation. Stopping after five records could miss the highest-starred repository and would undercount the totals.

Why use a fixed time in tests?

A repository can cross the seven-day boundary between test runs. Passing a time into the calculation makes that boundary testable without depending on the machine's clock.

Would concurrent page requests help?

Each next URL arrives with the preceding page, and more requests can encounter secondary limits. Start sequentially. For multiple organisations, a bounded worker pool may help; keep pagination within each organisation sequential and sort the merged results before printing.

Optional extensions

  • Authentication: read GITHUB_TOKEN from the environment and send it as a bearer token only to the configured API origin. Keep the public-repositories filter and exclude the token from errors and reports.
  • Caching: save response bodies with their ETags, send conditional requests, and handle 304 by reading the cached body. Cache each page with its pagination information.
  • Diff reports: add repository IDs to the saved report format, then compare reports by ID to show additions, removals, renames, and count changes.
  • Multiple organisations: add bounded concurrency, cancellation, and tests with controlled handlers. Run go test -race ./... with a host Go toolchain and C compiler.
  • History: save dated reports and plot star changes from those observations. The repository endpoint gives the current count, not a star-history series.
