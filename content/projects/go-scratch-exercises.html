Go Infra Track · Optional warm-ups

Predict it. Run it. Explain it.

Five small Go experiments about copies, shared memory, queues, and ownership.

Use these when a concept in a challenge feels unfamiliar. Each takes roughly 10–20 minutes, with extra time to explore. They are optional and are not part of your submission. Pair with AI: describe your prediction before asking it to help write the experiment, then explain any mismatch together.

Keep the programs in a scratch directory outside your challenge code. These are tasks to implement, followed by commands to run your programs and expected output. They deliberately leave function names and program structure to you.

mkdir go-warmups
cd go-warmups
go mod init example.com/go-warmups
mkdir values copies channels slices ownership

Give each folder a main.go. Print only the values requested, using fmt.Println, to compare with the output blocks. Predict first, run second, and change one thing at a time.

Experiment 1: Which counter changes?

Make a struct containing one integer counter. Write a function that takes the struct by value and increments its field. Call it with a variable initialized to zero, then print the caller's counter. Add another function that takes a pointer; call it with the same variable's address and print again.

Next, give the type two increment methods: one with a value receiver and one with a pointer receiver. Starting with a fresh zero counter, call the value method twice, then the pointer method twice. Print the caller's counter after each call.

Try it

Predict all six lines before running:

go run ./values
0
1
0
0
1
2

The value function and value method change their own copies. The pointer versions change the original variable. When a variable is addressable, Go can take its address for a pointer-method call; that convenience does not turn a value receiver into a pointer receiver.

Move the print inside the value function, after its increment, and predict the extra output. Seeing 1 inside and 0 outside is a useful clue when a handler appears to update a shared counter but the next request sees no change. Ask your AI partner to trace which variable each line reads.

Experiment 2: What did the copy share?

Make a struct with a string and an integer slice. Initialize it with "a" and []int{1, 2, 3}, whose length and capacity are both three. Assign the struct to a second variable. Through the second variable, change the string to "b" and slice element zero to 99. Print the first variable's string and slice.

Append 4 to the second variable's slice, storing the returned slice back into that field. Then change its element one to 42. Print the original slice, the second slice, and the original slice's capacity, each on its own line.

Try it

go run ./copies
a [99 2 3]
[99 2 3]
[99 42 3 4]
3

Copying a slice copies a descriptor pointing to an array, so both structs initially share elements. Assigning a new string field changes only that struct's field. The append needs a larger array because the slice was full; later element changes in the second slice no longer affect the first.

For a separate check in this folder, add a struct containing sync.Mutex and a counter, plus a function that accepts it by value, locks, increments, and unlocks. Call it once, without adding prints or concurrency. Predict what this command reports:

go vet ./copies
… passes lock by value …
… copies lock value …

These are diagnostic fragments; filenames, positions, and wording depend on your code and Go version. Expect a nonzero exit status. Each call receives a different lock, so the lock cannot coordinate access between copies. A Mutex must not be copied after first use; passing the containing state by pointer avoids this mistake. Fix the example and rerun vet: it should succeed with no diagnostics.

Experiment 3: Fill, drain, and close a queue

Create an integer channel with capacity two. Send 10 and 20, then print its length and capacity. With no receiver running, use a select to try sending 30, and a default case that prints full.

Close the channel, range over it while printing received values, then perform one more receive using the two-value form and print both results. Keep this version in a single goroutine so another receiver cannot change which case is ready.

Try it

go run ./channels
2 2
full
10
20
0 false

The default case makes the send attempt nonblocking. Closing preserves buffered values: the range drains 10 and 20 before it ends. Receiving from the closed, empty channel returns immediately with the element type's zero value and false.

Now add a final send on the closed channel and run the command again. After the same five lines, expect a panic containing send on closed channel and a nonzero exit status. Stack traces vary. Remove that final send when finished.

Predict what happens if you remove the default case instead. With the buffer full and no possible receiver, this version cannot make progress. In a concurrent service, checking len before sending is not a reservation: another sender could fill the space. Arrange ownership so the channel closes exactly once, after every sender has stopped.

Experiment 4: Reuse a batch buffer

Create a string slice with length zero and capacity four, then append "a", "b", "c". Print its length and capacity. Make a second slice using first[:0], append "x" to it, and print the first slice.

Start a separate case with a fresh length-zero, capacity-four slice containing a, b, c. Set u to the result of appending d to that slice. Set v to the result of appending e to the same original three-element slice. Print u and v.

Finally, start with the literal []string{"a", "b", "c", "d"}, whose capacity is four. Append e to make w, change w's first element to z, and print the original and w.

Try it

go run ./slices
3 4
[x b c]
[a b c e]
[a b c e]
[a b c d]
[z b c d e]

The first three appends that fit in spare capacity reuse existing storage. In the u/v case, both appends target the same fourth slot; the second overwrites d. The final case forces a new array because the original is full. The new capacity may vary; none of these expected results depends on its exact growth factor.

This is the batching hazard: resetting a slice's length does not detach its array. Before reusing it, establish that no other operation still needs the old contents. Ask your AI partner to help add a version that deliberately copies the elements, then explain the changed output using the append and copy rules.

Experiment 5: Who waits, and who closes?

Build a program that creates or truncates out.txt, writes three newline-terminated lines synchronously, and starts a goroutine for a fourth line. Give the goroutine an allowWrite channel: it must wait for a receive before touching the file. Have it signal a separate done channel after its write attempt. Check all file errors.

Use these explicit gates rather than sleeps. They establish an order even on a slow machine. For each variant, rerun the program from scratch so the file starts empty.

Try it

First, defer the file close and let main return without opening the gate or waiting. The goroutine cannot write its fourth line.

go run ./ownership
wc -l < out.txt
3

Second, close allowWrite to release the goroutine, then wait for done before returning and letting the deferred close run. Repeat those commands: expect 4 lines and no write error.

Third, explicitly close the file before releasing the gate, then release it and wait for done. Print the write error. Expect a message containing file already closed and a three-line file. Waiting for completion cannot repair a resource closed too early.

For two final variants, replace the file experiment. Register three deferred prints, labeled defer 1, defer 2, and defer 3, in that order, then return normally:

go run ./ownership
defer 3
defer 2
defer 1

Replace these with one deferred print followed by os.Exit(1). Run the built binary in a shell without set -e so you can inspect its exit code:

go build -o ownership-demo ./ownership
./ownership-demo
printf 'exit=%s\n' "$?"
exit=1

os.Exit skips deferred calls. No deferred message should appear. In your service, keep resources alive until their users finish, and complete cleanup before exiting. Explain who owns each close and what makes it safe; that explanation matters more than memorizing the output.
